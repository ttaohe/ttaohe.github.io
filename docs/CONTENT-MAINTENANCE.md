# 内容如何整理与维护

[返回 README](../README.md) · [网站设计](ARCHITECTURE.md) · [预览与发布](MANUAL-PUBLISHING.md)

## 从一个具体问题开始

技术笔记应让读者知道：这篇文章在回答什么问题，采用什么依据，结论适用于什么条件。

开头先交代动机和场景，再按问题展开机制与数据流。源码分析给出能够定位实现的版本和链接；论文解读说明作者的假设与实验条件。文章结尾可以收拢主要判断，再留下仍需要验证的问题。

阅读梳理、设计设想和实际复现需要明确区分。引用作者报告的性能结果时保留负载、硬件和统计口径；只有实际执行并保留结果的工作，才作为个人复现来描述。

## 正文、图源与摘要

正文以 Markdown 等可编辑形式保留，图表同时保存便于阅读的图片与可继续修改的源文件。这样修改网页样式或迁移托管环境时，不需要从已经生成的网页中反向恢复材料。

首页摘要用于帮助读者选择文章，可以比正文简短，但不能改变原文判断。图表应说明是在表达机制、条件路径还是实际测量，避免把示意图误读为性能结果。

简历也遵循同样的原则：可编辑源文件属于简历源仓库，主页使用生成后的 PDF；云盘副本承担备份用途。更新简历时，应同时核对源码、编译结果和网页中的下载版本。

## 让链接保持稳定

文章的 `slug` 在首次发布时确定。修改标题或补充段落时尽量保留它，让旧链接继续有效。移动页面前检查站内引用、关联文章和已分享的入口，再决定是否提供兼容跳转。

新增引用优先使用能够定位到论文版本、代码提交或原文段落的链接。对于会持续变化的页面，注明核验时间，方便后续读者理解文章当时的判断。

## 首页内容快照

`lib/blog/content.json` 为首页摘要和兼容页面提供结构化输入。它是经过核对的展示快照，不是放置未经确认材料的草稿箱。

| 字段 | 用途 |
| --- | --- |
| `slug`、`title`、`date` | 文章身份、标题与发布日期 |
| `summary`、`category`、`tags` | 首页的摘要与主题导航 |
| `outline`、`sections` | 保留目录和章节之间的对应关系 |
| `sources`、`disclosure` | 记录引用与核验边界 |
| `relatedSlugs` | 连接仍然公开的相关文章 |
| `daily` | 保留日报日期、条目、来源与主题信息 |

具体类型与兼容规则可以继续查看 [`lib/blog/types.ts`](../lib/blog/types.ts) 和 [`lib/blog/schema.ts`](../lib/blog/schema.ts)。历史快照中可能包含已经退出公开导航的栏目，修改时应先确认使用范围，不要因为文件里存在旧条目就重新发布它。

## 日报的审阅与归档

日报用于筛选值得跟进的新进展，每条保留原始来源，说明发生了什么以及为什么值得关注。旧事件出现实质新进展时，交代新增部分，避免反复收录同一条消息。

日报先交付待审版本，经确认后才进入公开归档。已发布期次按日期保存；补充或修订时保留原有文章和历史日期，不为了刷新页面而伪造新的更新时间。

## 一次修改怎样结束

内容写入成功只是中间状态。发布前还需要确认目录与正文对应、引用可以访问、关联文章仍存在、图片和图源能够打开，以及本次修改没有意外删除其他内容。

上线后回到真实网页检查标题、正文和来源。涉及简历时重新下载 PDF 核对；涉及导航和排版时检查宽屏与窄屏。只有这些结果一致，才将本次修改视为完成。

## 让首页反映持续研究

首页右栏的研究主线由 `portfolio/research-progress.json` 维护。每条主线用一个具体问题串联已经公开的文章；只有仍然存在的公开笔记才会出现在关联入口中。

更新足迹按笔记的实际日期排序。新笔记使用发布日期；经核对的修订可以在内容快照中填写 `lastRevisedAt`，并通过 `progressSummary` 简要说明新增的认识或修正。没有专门说明时使用配置中的摘要或文章标题，不推断已经掌握、完成实验或取得性能收益。

日报日期、网站构建时间和数据同步时间不会写成个人研究进展。没有新的笔记或修订时，保留真实的旧日期。新增材料仍遵循先审阅、再公开的流程。
